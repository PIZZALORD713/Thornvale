# Fresh-Player Playtests

Use fresh-player feedback to refine a complete phase, not to approve every
feature while it is being built. The current phase contract remains authoritative in
[`../../wiki/Plan-2.0.md`](../../wiki/Plan-2.0.md).

## Phase workflow

1. Build the bounded phase in broad strokes until its complete player route and
   technical criteria pass.
2. Publish a stable checkpoint and add a short questionnaire tailored to the
   phase's experience hypothesis.
3. Invite fresh players as they are available. Do not pause phase implementation
   for human approval of individual features or wait on a fixed participant quota
   before useful work continues.
4. Review feedback as it arrives. Interrupt work for reproducible progression,
   save-integrity, security, provenance, or release failures; carry ordinary
   confusion, pacing, and preference observations into the refinement pass.
5. Look for early patterns after roughly three sessions. Five or more comparable
   sessions improve confidence for major scope or public-release decisions but
   are not an automatic development gate.
6. Run a bounded refinement pass, record what changed, and retest material
   changes when useful.

The qualified Phase 1 checkpoint is recorded in
[`2026-07-16-m1-day-one-cohort.md`](2026-07-16-m1-day-one-cohort.md). It remains
a reproducible reference build, not a mandate to freeze all subsequent work.

## Run a session

1. Copy [`FRESH-PLAYER-TEMPLATE.md`](FRESH-PLAYER-TEMPLATE.md) to
   `YYYY-MM-DD-session-XX.md`, or capture the same minimum fields in rough notes
   for an agent to format afterward.
2. Record the build label or URL and input method. Exact hashes, browser versions,
   and viewport details are optional unless diagnosing a technical failure or
   comparing variants.
3. Start from a clean browser profile or cleared ThornVale storage. Use a player
   who has not watched the route or received story instructions.
4. Let the player think aloud if comfortable. Do not teach controls, explain the
   story, point toward objectives, or interpret an anomaly unless the player asks.
5. Note where help was required to continue; exhaustive timestamps are optional.
6. Ask the short phase questionnaire before explaining intent or showing the other branch.
7. Hand rough notes, answers, or an authorized recording to an agent for formatting
   and synthesis instead of making the facilitator perform administrative work.

Use a session ID rather than a participant name. Retain recordings, screenshots,
or direct quotes only with permission, and do not record unnecessary personal data.

## Preserve observation quality

- Record behavior or the player's words before interpretation.
- Separate progression blockers, friction, confusion, delight, and suggestions.
- Record a new build label after material runtime changes. Perfect cohort purity
  is necessary only for an explicit comparison, not ordinary phase feedback.
- For baseline-versus-pilot tests, assign one condition per fresh participant.
  Showing both conditions teaches the route and invalidates a fresh comparison.
- Keep failed and incomplete sessions. They are evidence, not bad data.

## Synthesis

Agents should:

- aggregate completion, duration, help, anomaly recognition, theme comprehension,
  choice distribution, verified consequences, and replay interest;
- preserve exact observations separately from interpretations;
- group repeated friction by route stage and severity;
- compare cohorts only when build and study conditions permit it;
- rank the smallest evidence-backed changes before recommending new content; and
- distinguish immediate technical blockers from refinement findings;
- recommend the smallest repeated-evidence refinements without stopping unrelated
  broad phase work.

Do not invent missing observations or convert one player's preference into a
product conclusion.
